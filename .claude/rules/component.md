# A serde format crate

serde_markdown maps a Rust value onto a Markdown document and back through
serde: fields at the start (a YAML, JSON, or TOML fence, or the same
mapping without a fence), body sections after them, the last body field
the rest of the document, verbatim. It is a general-purpose library;
Knowqore is its anchor consumer (`consumers.md`).

## The API is serde, not a proto contract

The caller passes its own value — `to_string(&value)`,
`from_str::<T>(text)` — with its own serde attributes and
`#[derive(Markdown)]`. The owner decided (7 October 2026) not to move the
API onto a protobuf service generated by `protoc-gen-contract-rust`: a
proto method takes one concrete message, so every caller would convert its
struct into a generic value message and back, and its serde attributes
would stop mattering. Do not propose it again without a new reason.

## One channel to consumers

A consumer gets everything through the Cargo dependency: the crate by git
tag. The `(markdown.body)` option ships inside the crate
(`rust/markdown/proto/markdown/options.proto`); a build script reaches it
through `PROTO_INCLUDE`, Bazel through a crate_universe annotation on the
crate's repository (README, "Proto option"). Never a `bazel_dep` as well:
two channels for one library drift apart (Knowqore once pinned Cargo
`v0.3.1` and `bazel_dep` `0.2.3`).

Anything a consumer needs at build time lives inside the crate's
directory, `rust/markdown`: crate_universe fetches a git crate with
`strip_prefix` set to that directory, so a file outside it never reaches
the consumer.

```text
# BAD — a file consumers need, outside the crate
proto/markdown/options.proto

# GOOD — inside the crate, under its own proto/
rust/markdown/proto/markdown/options.proto
```

## Async form, native

Callers are async from top to bottom. Feature `tokio` (off by default,
owner, 7 October 2026) gives every public function an async twin under the
same name in `serde_markdown::tokio`. The twin is native, never the sync
function moved to the blocking pool: writing and reading are each one
algorithm written as a `Steps` job (`src/drive.rs`). The sync function runs
the steps; the async one runs the same steps and calls
`tokio::task::consume_budget().await` between them. A new public function
gets its twin in the same change, and new work goes into steps, not into a
second copy of the algorithm.

```text
# BAD — the async twin is the sync function on the blocking pool
pub async fn to_string<T>(value: &T) -> Result<String, Error> {
    let value = value.clone();
    spawn_blocking(move || crate::to_string(&value)).await?
}

# GOOD — the same job, a yield point between its steps
pub async fn to_string<T>(value: &T) -> Result<String, Error> {
    drive::run_async(WriteDoc::new(value, Format::Yaml, FieldsLayout::Fenced)).await
}
```

## Call direction

The library knows nothing of its caller. It never names Knowqore's crates,
types, paths, or domain.
